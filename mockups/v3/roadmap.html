MyCaddiPro · from 1.0 to 3.0 · prepared 3 September 2026 · nothing in this document has been built or deployed

One app, built to be run from a tee box, and built so it can keep changing.

1.0 got a real product into daily use: 3 societies, 57 events on the calendar this month, 271 rounds scored in the last 30 days. It did it as a single 9.7 MB web page that every phone re-downloads on every open, with a database any visitor can write to. 3.0 keeps everything that works, puts it in a shell that loads in a second, gives each role its own phone and desktop product, and closes the security hole. Below: what it costs today, what changes, what never changes, and every screen, before and after.

The verdict in five lines

  • Speed. The golfer opens the app in about a second on 4G instead of parsing 8.9 MB of JavaScript every time. The shell is cached; only the screen you open is downloaded.
  • Zero re-entry. The system already knows your event, course, nines, group, caddy, van and fees. 3.0 shows them and asks for a tap, never for the data again. Play Golf becomes one button. Organizers stop re-picking the event in five tabs.
  • Two products, not one stretched page. Phone: one-thumb, a "leave at" band, a bottom bar. Desktop: rails, panes, tables, boards, nothing centered in a 1280 px column.
  • Secure by design. Sessions carry identity, row-level policies enforce it, the public key can read public boards and nothing else. Today 156 of 161 tables are open to anyone.
  • Changeable. One handicap resolver, one fee calculator, one payment writer, one toast, one dictionary lookup, typed against the real database. A wrong table name fails the build, not a golfer mid-round.

The 3.0 architecture, in one picture

Same Supabase database, same LINE login, same URLs. What changes is everything between the golfer's thumb and the database row.

Shell
One app shell per platform
  • Phone: status band, bottom bar, sheets
  • Desktop: rail, top strip, panes
  • Installed PWA + Capacitor iOS/Android from the same code
  • Cached; screens load as small chunks
Screens
Modules per role, one design system
  • The kit you see in every mockup = real tokens and components
  • No inline handlers, no globals
  • EN/TH/KO/JA through one lookup
  • Each screen has a parity checklist vs 1.0
Engines
One of each
  • Handicap resolver (DB, already the anchor engine)
  • Fee calculator · payment writer
  • Scoring engine (the tested one) + offline queue
  • Notification pipeline (in-app · LINE · digest)
Data & auth
Typed, scoped, observable
  • Client generated from the schema
  • Writes through RPC/edge with validation
  • JWT sessions (Auth v2 groundwork exists) + scoped RLS
  • Errors and performance tagged by release

Offline-first scoring

Scores are written locally first and synced when signal returns. The card shows "Saved · 0 queued". A dead spot on hole 12 never blocks the keypad, never loses a hole, never double-writes. Today a lost request is a lost score.

Strangler cutover, not a big bang

The 3.0 shell goes live first and hosts 1.0 screens unchanged inside it. Each role is switched to its 3.0 screens only when its parity checklist is green. Golfers first, organizers second, staff third. 1.0 is retired when nothing points at it.

What never changes

Your decisions stay decided

  • Play Golf is the ▶ triangle, exactly as you specified.
  • The TRADV paper scorecard is the scoring view; the keypad rides it.
  • Poster cube art stays. Flat icon sets stay rejected.
  • No purple. Green #22c55e is the highlight. Compact chrome. Full monitor width.

The data and the doors

  • Same Supabase project, same tables, same handicap engine and triggers. No migration weekend.
  • LINE, Kakao and Google login. Staff PINs. Society PINs.
  • mycaddipro.com, the LINE bot, the TRGG website pull.
  • Society isolation absolute, on every surface.

The doctrine

  • Evidence before theory; every surface before "the" surface.
  • Mockup is the spec: every approved frame ships 1:1.
  • Verified at 360–390 px on the live site before "done".
  • FUCKUPS ledger keeps growing; each rule keeps its case law.

"Everything must work": how that is enforced, not promised

Parity checklist per screen

Before a 3.0 screen replaces its 1.0 counterpart, every element id, action and data field of the old screen is listed and marked present, moved, or cut with your sign-off. This is the FUCKUPS #39 lesson (the TRADV view shipped without the pin mirror) made mechanical.

Per-role switch, instant rollback

Each role's cutover is a flag. If a Tuesday event finds a gap, the organizer role flips back to 1.0 screens in the same shell within a minute, data untouched, while the gap is fixed.

Flow tests that drive the real app

Login both ways, start a round from the tee sheet, score 18 holes with the network cut, end, see the result, register for an event with a van, run a tee sheet, publish results. Run on every release at phone width. Screens are also diffed against the approved mockup frames.

Live-ops stays possible

The database is unchanged, so every SQL live-ops move you can make today still works mid-round. Errors arrive grouped by signature with the release tag, so "is it new" is one glance.
